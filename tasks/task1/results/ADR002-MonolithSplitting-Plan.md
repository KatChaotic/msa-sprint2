### <a name="_qmphm5d6rvi3"></a>**Решение**

**[Описание целевой архитектуры микросервисов](./ADR001-MonolithSplitting.md)**

Полноценная разработка всех микросервисов не представляется возможным из-за небольшого объема ресурсов разработки, поэтому необходимо начать миграцию постепенно используя паттерн **[Strangler-Fig](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig)**.

Некоторые сервисы монолита сильно связаны и их выделение может быть сложным шагом для перехода на микросервисную архитектуру, особенно если у команды отсутствует опыт разработки микросервисов.

**1. Вынесение микросервиса пользователей**

Первым логичным шагом является вынесение сервиса пользователей в отдельный микросервис, т.к. данный сервис не имеет зависимостей и его вынесение будет простой задачей.
Необходимо вынести АПИ в отдельный микросервис и провести прямую миграцию данных.

**2. Подключение BFF**

При появлении первого микросервиса, необходимо начать внедрение BFF для роутинга запросов от Frontend

**3. Микросервис отелей**

Сервис отелей так же является низко-связанным  сервисом и его вынесение в отдельный микро-сервис с собственной базой данных так же будет являться простой задачей.

**4. Вынесение микросервиса отзывов**

Сервис отзывов так же является низко-связанным  сервисом и его вынесение в отдельный микро-сервис с собственной базой данных так же будет являться простой задачей.

**5. Вынесение микросервиса бронирования**

Основные связанные сервисы, необходимые для работы бронирования уже вынесены в отдельные микросервисы. 
Необходимо будет выделить задачу проверки полного бронирования отеля в новый микросервис.

**6. Вынесение микросервиса промокодов**

Вынесение последнего сервиса с логикой в отдельный микросервис, после которого будет возможно отключение монолита.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

В качестве альтернативы можно пойти от сложного к простому.

**1. Вынесение микросервиса бронирования**

Данный сервис является одним из высоконагруженным и его масштабирование может быть одним из важных факторов для выбора его в качестве первого микросервиса для выделения.
Благодаря использованию кеширования между сервисами пользователей, отелей и отзывов сервис не создаст перегрузки на монолит при обращении к промокодам. Для минимизации риска остановки сервиса для пользователей рекомендуется использовать отдельный экземпляр монолита, который будет обеспечивать потребности нового микросервиса.

**2. Вынесение микросервиса промокодов**

Данный сервис так же является высоконагруженным за счет постоянного обращения от сервиса бронирования, поэтому необходимо вынести его следующим, чтобы обеспечить простую масштабируемость системы.

**Недостатки, ограничения, риски**

1. В текущем плане есть возможный риск отказа сервиса бронирования за счет появления внешних HTTP запросов для валидации данных, что может приводить к ухудшению пользовательского опыта
